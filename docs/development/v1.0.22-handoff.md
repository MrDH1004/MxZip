## 종료 crash 해결 (집 PC, 2026-11-01)

native stack 확보 결과, crash는 Python/Qt 정리 단계가 아니라 **프로세스 종료 시 DLL detach** 안에서 난다.

```text
os._exit → ucrtbase → kernel32!ExitProcess → ntdll 로더 종료 (DLL_PROCESS_DETACH)
 → shiboken6 CRT atexit 테이블 → Shiboken::BindingManager::~BindingManager
 → Object::destroy → Object::invalidate → BindingManager::releaseWrapper
 → mov rbp,[rax+rsi*8] (rax=0: 이미 무효인 래퍼의 C++ 포인터 배열이 null)
```

- 수집: Win32 debug loop(`WaitForDebugEvent` + dbghelp `StackWalk64`)로 second-chance AV 시점의 스택을 기록, 보이지 않는 별도 데스크톱(`CreateDesktop`)에서 실제 win32 플랫폼으로 실행. offscreen에서는 재현되지 않음.
- 기호: REA(Ghidra)로 `shiboken6.abi3.dll` 오프셋을 함수 이름으로 해석.
- `~BindingManager`는 `Py_IsInitialized()`가 참이면 남은 래퍼를 모두 destroy한다. `os._exit`는 Python을 finalize하지 않으므로 이 경로가 항상 실행되고, 이미 Qt 쪽에서 지워진 객체의 래퍼가 남아 있으면 null을 읽는다. 종료 직전 정리를 어떻게 바꿔도 detach 단계 자체는 그대로라 이전 가설 1~3이 모두 실패했다.
- 수정: `appcore.hard_exit()` — Python stdio flush 후 `TerminateProcess(GetCurrentProcess())`. DLL detach를 건너뛴다. `mxzip_main.py`, `mxzip_gui.finish`, 두 `__main__`의 예외 경로가 모두 이 함수로 끝난다. atexit·QSettings·logging 핸들러 등 detach에 의존하는 코드는 없다(기존 `os._exit`도 atexit을 실행하지 않았음).
- 회귀 테스트: `test_hard_exit.py` (FLS 콜백으로 로더 종료 단계 실행 여부를 판별 — `os._exit`는 실패, `hard_exit`는 통과).
- 결과: 수정 전 단독 80회 중 5회 crash → 수정 후 단독 100회 0회, 동시 3프로세스 50라운드 0회, `exe_verbs_smoke.py` 57/57 × 3회.

함께 반영:
- `lzmamt.write_7z`: 암호 없는 7z의 헤더를 LZMA2로 인코딩(kEncodedHeader, 7z 공개 포맷). 1,500개 작은 파일 7z가 132,272 → 9,903바이트(the third-party archiver 10,456). 4 MB 넘는 헤더는 preset 1. 암호 7z 헤더는 py7zr 호환 때문에 기존처럼 AES만.
- `nativeaccel/build.ps1`: vcvars의 stderr 경고가 PowerShell 5.1에서 빌드 실패로 처리되던 문제.
- 환경 의존 테스트 정리: 한국어 Windows의 cp949 PowerShell 오류 출력, symlink 권한 없음은 skip, git에 없는 `.superpowers` 파일 의존 테스트는 파일이 없으면 skip.

## (해결됨) 이전 배포 차단 문제

Explorer의 `--archive` 경로는 압축 결과를 정상 생성한 뒤 프로세스 종료 과정에서 간헐적으로 native crash가 발생한다.

- 종료 코드: `0xC0000005`
- WER 장애 모듈로 관찰된 파일:
  - `shiboken6.abi3.dll`
  - `pyside6.abi3.dll`
  - 일부 실험에서 `ucrtbase.dll`과 `0xC0000409`
- 동시 실행이 필수 조건이 아니며 단독 실행에서도 재현
- 충돌 시에도 생성된 archive와 내용은 정상
- `error.log`는 비어 있음

실패한 가설과 처리:

1. Qt 없는 `--archive` fast path
   - crash는 제거했지만 기존 progress/cancel/error UI가 사라지고 IPC 종료 경쟁을 새로 만들어 채택하지 않음
   - 커밋 `a566b5a`를 `bbca595`에서 완전히 revert함
2. 종료 시 강제 `gc.collect()` 제거
   - 단독 3회째 같은 Shiboken crash가 재현돼 폐기
3. `DeferredDelete`, GC 등 explicit Qt cleanup 전체 우회 후 즉시 종료
   - 단독 2회 중 1회 crash가 재현돼 폐기

(당시 판단, 위 절에서 해결됨) 같은 계열의 추측성 종료 패치를 더 쌓지 않는다. 다음 단계는 native crash stack을 확보한 뒤 구조를 재검토하는 것이다. 현재 권장 구조 후보는 장기 실행 Qt broker가 IPC와 progress UI를 소유하고 Explorer의 단명 프로세스는 Qt를 생성하지 않는 방식이다. 기존 기능과 IPC 경계를 명세한 뒤 별도 설계·TDD로 진행한다.
